  1. Search uses the same normaliser as the public explorer and the Publish Engine (Persian/Arabic digits, separators, ×). Equivalent spellings find the product itself; suffix variants such as 6205-2RS find their base series but are shown as variants, never as the same product.
  2. Dimensions use each family's own symbols (d×D×B, Fw×D×C, d×D×H, d×D×T), read from SpecValue rows and never typed as a string.
  3. Sources: core values with a cited Source out of core values required. Red means a core value has none. For housings and units, the core list is set in Phase 3 (shown as ?).
  4. Two independent states. Status (draft / published / archived) and Verification (pending / verified). Together they decide explorer visibility, robots, sitemap and structured data, using the section K table.
  5. "Show in Product Explorer" is its own flag (D9/C1). Pending products can be discoverable and still be noindex.
  6. Translation completeness is shown per language. Persian and English are separate fields and are never auto-translated.
  7. Bulk actions are deliberately few. Archive asks for confirmation and shows the URL consequence (410 or 301, decided in Phase 3). Bulk-verify does not exist: verification is per product, by the Owner.
  8. Catalogue import (approved in principle) is a repeatable, validated importer. CSV is one supported input, not the only path. Every run produces a reconciliation report; unsourced values land as "pending" and imported products as drafts. See the migration plan below.

  1. Same structure as the public workspace (Overview · Dimensions & data · Media · Documents · SEO). Overview holds summary, applications and notes, with fa and en fields side by side.
  2. Spellings are not variants. Equivalent spellings (same designation written differently) are rarely needed because the normaliser handles spacing, hyphens and digits. جایگزینی در همان محل 5حذف

حذف ممکن نیست: این فایل ۲ ارجاع دارد. ابتدا ارجاع‌ها را بردارید.

  1. Upload pipeline (section J): MIME sniffing plus magic bytes, re-decoding, strict SVG sanitising, content-hash rename, EXIF strip and auto-orient, then 320/640/1024/1600 widths. Limits are configurable and capped by the host's upload_max_filesize, which the probe will confirm.
  2. One alt-text rule, shared with A7. ALT-INF: an informative image used in a language release needs alt text in that language. If it is missing, Publish blocks that content in that language until you add the text, mark the image decorative, or remove it from that language version. A decorative image outputs alt="" and needs none. ALT-UNUSED: unused images with missing alt are only a library notice and never block Publish.
  3. Variants and dimensions are recorded, so public pages always get width/height (zero CLS) and srcset. If the host lacks WebP or AVIF support, optimised JPEG/PNG is used instead.
  4. Reference counting: "Used by" lists every entity that points at the file. Delete is blocked while any reference exists. Unreferenced files go to a 30-day trash before physical deletion.
  5. Replace in place keeps every reference and changes the hash, so caches refresh without editing any product.
  6. PDF datasheets appear as Document entities, with title, language, version, product and family links, and show their size and page count publicly. There is no in-page viewer.

Designation policy: spellings vs variants (proposed data model, not built)

6205, 6205-2RS and 6205-ZZ are different designations. They share boundary dimensions but differ in sealing, and possibly in speed limits and mass. Search may lead from one to another, but the system must never treat them as the same request.

  • Spelling (separate table): another way of writing the same designation. Its normalised key is unique across products, variants and spellings, and it is never used for suffixes.
  • Match precedence (same normaliser on site, Publish Engine and Admin): exact (designation or spelling) › variant (listed variant) › series (a listed designation plus an unlisted suffix: the listed one is the base series) or related (the plain designation of a listed suffixed one, e.g. 6305 for 6305-2RS: the listed one is a variant of the request, never its base) › none. The prototype uses a simple suffix rule; Phase 3 replaces it with a per-family suffix list managed in the Admin.
  • Public contract: the requested designation is shown and carried verbatim (workspace title, copy, link, WhatsApp, inquiry). A variant without sourced variant-specific data is presented as "Base series match — requested variant requires confirmation", never as an unqualified verified match. When the plain designation is asked and only a suffixed one is listed (6305 → 6305-2RS, 22220 → 22220 E), the site says "Related match — requested designation requires confirmation" and never calls the listed one the base.
  • Indexing: only base product URLs are indexed. A variant request (/p/6205?r=6205-2RS; #p-6205:6205-2RS in the prototype) has its canonical on the base. A variant gets its own indexable URL only once it has verified variant-specific data.
  • Inquiry record: requested_raw, requested_norm, match_type, product_id, variant_id (nullable). Admin matching (A6) reads these fields and never re-guesses.

Catalogue migration — Phase 3 plan (nothing is migrated in this round)

CSV is one supported input, not the only path. The goal is a repeatable, auditable import that can never quietly turn unverified data into "verified".

  1. 1 · Audit the existing source of truth. Inventory the current catalogue (old site database or export, spreadsheets) and record for each field where it came from and how trustworthy it is.
  2. 2 · Repeatable, validated importer. A dry-run first, then an idempotent run keyed on normalised designation. Inputs: CSV or the old system's export. The same validation as the editor applies: controlled spec keys, units, D > d, unique keys, and spellings kept separate from variants.
  3. 3 · Keep provenance only where it is trustworthy. A value that carries a citable source keeps it as a Source and SpecValue link. Anything else is imported without a source.
  4. 4 · Safe defaults. Unsourced or unverified values land as pending (shown as pending publicly). Imported products land as drafts, and nobody is "Verified for indexing" automatically.
  5. 5 · Reconciliation report after every run. Created, updated, skipped and conflicting rows; values without a source; designations whose suffix needs a variant decision; duplicates and near-duplicates. Nothing is published until an Owner reviews it.

Admin UX standards

  • Inline validation next to the field, with save feedback and an unsaved-change guard.
  • Confirmation dialogs only for destructive or public actions (archive, delete, restore, rollback, publish).
  • Every list has an empty state and an error state; empty states explain the next step (e.g. "No inquiries yet — they arrive from the site form").
  • Persian UI, RTL, Vazirmatn; codes, dimensions, units, phone numbers and release IDs are always Latin JetBrains Mono; ordinary counts use Persian digits.
  • Minimum label size 13 px, 34 px controls (46 px on touch), visible focus ring, full keyboard operation, WCAG 2.2 AA contrast.
  • Server-rendered PHP pages with a little vanilla JS (tabs, chips, upload progress). No SPA framework; admin assets live under /admin and are never referenced by public pages.
